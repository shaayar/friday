## SECTION 2 — WHERE DOES THE LLM GET ITS CONTEXT?

### 2.1 LiveKit's Context Architecture

```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                           CHAT CONTEXT FLOW                                         │
└─────────────────────────────────────────────────────────────────────────────────────┘

session._chat_ctx (global, all turns)
    │
    ├─ Updated on: user message, assistant message, tool call, tool result, handoff
    │
    ▼
agent._chat_ctx (agent-scoped, copy of session at start + agent-specific)
    │
    ├─ Created in Agent.__init__: chat_ctx.copy(tools=self._tools)
    ├─ Updated via: agent.update_chat_ctx()
    └─ Used in: _pipeline_reply_task() → chat_ctx.copy() → modifications
                    │
                    ▼
            llm.chat(chat_ctx, tools, ...)  ← ACTUAL LLM REQUEST
```

### 2.3 Answers to Key Questions

| Question | Answer |
|----------|--------|
| **1. Where does LiveKit store conversation messages?** | `session._chat_ctx` (global) and `agent._chat_ctx` (agent-scoped). Both are `ChatContext` objects containing `ChatItem` list (ChatMessage, FunctionCall, FunctionCallOutput, AgentHandoff, AgentConfigUpdate). |
| **2. What object contains current chat history?** | `agent._chat_ctx` (read-only via property, returns `_ReadOnlyChatContext` wrapper). |
| **3. Where is LLM request constructed?** | `AgentActivity._pipeline_reply_task_impl()` → `perform_llm_inference()` → `agent.llm_node(chat_ctx, tools, model_settings)` → `activity.llm.chat(chat_ctx, tools, ...)`. |
| **4. Where are system instructions injected?** | In `_pipeline_reply_task_impl()` lines 3050-3064: modality-aware `instructions.render()` added as system message. |
| **5. Where are user messages added?** | In `_generate_reply()` → `_pipeline_reply_task()` → `_pipeline_reply_task_impl()` line 3046-3047: `chat_ctx.insert(new_message)`. |
| **6. Where are tool calls/results represented?** | As `FunctionCall` and `FunctionCallOutput` items in `ChatContext.items`. Injected via `_inject_running_tool_calls()` and tool executor callbacks. |
| **7. Can custom chat context be supplied?** | **YES** — `generate_reply(chat_ctx=custom_ctx)` parameter overrides the default. Also `agent.update_chat_ctx(new_ctx)` replaces the agent's context. |
| **8. Can LLM receive dynamically assembled context?** | **YES** — pass `chat_ctx` to `generate_reply()` or update `agent._chat_ctx` before the turn. |
| **9. Can context be modified immediately before LLM call?** | **YES** — override `Agent.on_user_turn_completed(turn_ctx, new_message)` which receives the `turn_ctx` (copy of chat context) and `new_message` BEFORE `_generate_reply()` is called. |
| **10. Does native tool calling still work with custom context?** | **YES** — tools are passed separately to `llm.chat(chat_ctx, tools=tools)`. The LLM sees both the custom context AND the tool definitions. |

## SECTION 4 — CONTEXT MANAGER INTEGRATION

### 4.1 Proposed Flow

```
User Speech
    │
    ▼
STT → Transcript (ChatMessage)
    │
    ▼
AgentActivity._on_final_transcript()
    │
    ▼
commit_user_turn() → inserts user message into agent._chat_ctx + session._chat_ctx
    │
    ▼
Agent.on_user_turn_completed(turn_ctx, new_message)  ← HOOK POINT
    │
    ├─ turn_ctx = copy of agent._chat_ctx (includes new_message)
    ├─ Retrieve recent_messages from turn_ctx.messages()
    ├─ Get conversation_id from session.userdata
    ├─ Get active_project_id from ProjectService
    ├─ ContextManager.assemble(
    │       system_instructions=persona.md,
    │       current_user_message=new_message.text_content,
    │       recent_messages=recent_messages,
    │       conversation_id=conversation_id,
    │       active_project_id=active_project_id
    │   )
    │
    ▼
ContextSnapshot
    │
    ▼
Build custom ChatContext from snapshot.render() or structured items
    │
    ▼
await agent.update_chat_ctx(custom_chat_ctx)  # OR pass to generate_reply()
    │
    ▼
_generate_reply() → _pipeline_reply_task() → llm.chat(custom_chat_ctx, tools)
```

### 4.2 Detailed Mapping

| FRIDAY Input | Source | Conversion |
|--------------|--------|------------|
| `system_instructions` | `persona.md` via `load_system_prompt()` | String → system `ChatMessage` |
| `current_user_message` | `new_message.text_content` | String → user `ChatMessage` |
| `recent_messages` | `turn_ctx.messages()[-N*2:]` | `ChatMessage` → `(msg_id, role, content)` tuples |
| `conversation_id` | `session.userdata["conversation_id"]` | int/str |
| `active_project_id` | `ProjectService.active_project().project_id` | str or None |

### 4.3 Converting LiveKit Messages → ContextManager Messages

```python
def lk_messages_to_context_messages(lk_messages: list[ChatMessage]) -> list[tuple[str, str, str]]:
    """Convert LiveKit ChatMessage list to ContextManager Message tuples."""
    result = []
    for msg in lk_messages:
        # msg.id is LiveKit's shortuuid (string)
        # msg.role is "user" | "assistant" | "system" | "developer"
        # msg.text_content returns combined text
        content = msg.text_content or ""
        if content.strip():
            result.append((msg.id, msg.role, content))
    return result
```

### 4.4 Building Custom ChatContext from ContextSnapshot

```python
def snapshot_to_chat_context(snapshot: ContextSnapshot) -> ChatContext:
    ctx = ChatContext.empty()
    
    # 1. System instructions
    if snapshot.system_instructions:
        ctx.add_message(role="system", content=[snapshot.system_instructions])
    
    # 2. Current user message
    if snapshot.current_user_message:
        ctx.add_message(role="user", content=[snapshot.current_user_message])
    
    # 3. Recent messages (already in turn_ctx, but we may want budgeted subset)
    for msg_id, role, content in snapshot.recent_messages:
        ctx.add_message(role=role, content=[content], id=msg_id)
    
    # 4. Project context
    if snapshot.project_context:
        ctx.add_message(role="developer", content=[snapshot.project_context])
    
    # 5. Durable memories
    if snapshot.durable_memories:
        mem_text = "\n".join(f"- {m.content}" for m in snapshot.durable_memories)
        ctx.add_message(role="developer", content=[f"Relevant memories:\n{mem_text}"])
    
    # 6. Compressed history
    if snapshot.compressed_history:
        ctx.add_message(role="developer", content=[f"Previous context summary:\n{snapshot.compressed_history}"])
    
    return ctx
```

### 4.5 Avoiding Duplicate Conversation History

**Critical:** LiveKit's `turn_ctx` already contains the full conversation history. If we build a custom `ChatContext` from `ContextSnapshot`, we must **replace** not **merge**.

```python
# In on_user_turn_completed:
async def on_user_turn_completed(self, turn_ctx: ChatContext, new_message: ChatMessage):
    # Extract what we need from turn_ctx
    recent_lk_messages = turn_ctx.messages()[-20:]  # last 10 turns
    
    # Assemble FRIDAY context
    snapshot = self.context_manager.assemble(
        system_instructions=...,
        current_user_message=new_message.text_content,
        recent_messages=lk_messages_to_context_messages(recent_lk_messages),
        conversation_id=...,
        active_project_id=...
    )
    
    # Build REPLACEMENT context (not additive)
    custom_ctx = snapshot_to_chat_context(snapshot)
    
    # Replace agent's context for this turn
    await self.update_chat_ctx(custom_ctx)
```

### 4.6 Preventing LiveKit's History from Defeating Budget

The `ContextManager` already enforces budget via `estimated_units`. Since we replace the entire context with our budgeted snapshot, LiveKit's unlimited history is **not sent to the LLM**. The `chat_ctx` we pass to `update_chat_ctx()` IS the budgeted context.

## SECTION 5 — MEMORY LIFECYCLE

### 5.1 When Should Extraction Occur?

**Recommendation: After assistant response completes (post-turn), async, every N turns.**

```python
# In agent_friday.py or AssistantSession:
async def on_assistant_response_completed(self, user_msg, assistant_msg):
    turn_count += 1
    if turn_count % EXTRACTION_CADENCE_TURNS == 0:
        # Fire-and-forget background task
        asyncio.create_task(run_memory_extraction(
            conversation_id=conversation_id,
            recent_messages=get_recent_messages(conversation_id),
            project_id=active_project_id
        ))
```

### 5.2 Rationale

| Factor | Analysis |
|--------|----------|
| **Latency** | Extraction calls LLM → 1-3s. MUST NOT block voice response. |
| **Reliability** | Failures must not break conversation. Background task with try/except. |
| **Duplicate extraction** | Track last extracted message_id; only extract new messages. |
| **Provenance** | `MemoryExtractor` requires `conversation_id` and message IDs — available after persistence. |
| **Failure isolation** | `MemoryExtractor` already isolates LLM failures (logs warning, returns []). |

### 5.3 NOT on these triggers:

| Trigger | Why Not |
|---------|---------|
| Every turn | Too much LLM latency/cost; extraction is expensive |
| Before next turn | Blocks user speech → higher perceived latency |
| After compaction | Compaction is less frequent; extraction should be more frequent |
| Background task (continuous) | Harder to coordinate with conversation boundaries; per-turn cadence is simpler |

## SECTION 6 — COMPACTION LIFECYCLE

### 6.1 Current Design (from ADR-025, compaction code)

- `ConversationCompactor.compact(messages, conversation_id, force=False)` — single bounded window
- Trigger: `should_compact(eligible_count, estimated_units, force, message_threshold=20, unit_threshold=4000)`
- Compaction advances boundary (`next_compaction_start` from persisted compactions)
- Promotion is **explicit, downstream, optional** — `ConversationMemoryPromoter.promote(compaction, project_id)`

### 6.2 M7 Recommendation: C — Expose Explicit Runtime Service, Defer Automatic Triggering

```python
class CompactionService:
    def __init__(self, compactor: ConversationCompactor, promoter: ConversationMemoryPromoter):
        self._compactor = compactor
        self._promoter = promoter
    
    async def maybe_compact(self, conversation_id: int, messages: list[Message]) -> CompactionResult | None:
        """Call after each turn. Runs compaction if threshold met."""
        result = self._compactor.compact(messages, conversation_id=conversation_id, force=False)
        if result.compacted:
            # Promotion is explicit per ADR-025 — caller decides
            pass
        return result if result.compacted else None
    
    async def force_compact_and_promote(self, conversation_id: int, messages: list[Message], project_id: str) -> PromotionResult:
        """Explicit invocation for testing/admin."""
        result = self._compactor.compact(messages, conversation_id=conversation_id, force=True)
        if result.compacted:
            return self._promoter.promote(result.compaction, project_id=project_id)
        return PromotionResult(compaction_id="", items=())
```

### 6.3 Why Not Automatic Per-Turn (A) or Background (B)?

| Approach | Problem |
|----------|---------|
| **A. Per-turn automatic** | Compaction calls LLM → adds 2-5s latency if synchronous. If async, race conditions with ongoing turns. |
| **B. Background worker** | Needs separate process/thread; SQLite locking complexity; harder to test; voice latency unaffected but operational complexity high. |
| **C. Explicit service (RECOMMENDED)** | Caller controls when. M7.1 can call `maybe_compact()` after turn in background task. Promotion remains explicit. Simpler, testable, no new infrastructure. |

**M7.1 Implementation:** Add `CompactionService.maybe_compact()` call in a fire-and-forget task after assistant response. Do NOT await it.

| Resource | Owner | Rationale |
|----------|-------|-----------|
| `conversation_id` | `AssistantSession` | Created at session start; persists for session lifetime |

### 7.2 `AssistantSession` — Justified?

**YES.** The readiness review identified "no orchestration layer." `AssistantSession` is NOT a large Session model — it's a **lifecycle owner** that:

1. Constructs and holds all stores/managers
2. Provides `process_user_message()` method that orchestrates one turn
3. Ensures proper shutdown order (stores close AFTER LiveKit session)
4. Enables testing (inject fake stores/LLM)

It does NOT:
- Track task execution state (ADR-026 defers this)
- Manage agent registry/workers
- Handle multi-agent coordination

## SECTION 8 — CANONICAL MESSAGE REPRESENTATION

### 8.1 Current Representations

| Representation | Type | Fields | Used By |
|----------------|------|--------|---------|
| LiveKit `ChatMessage` | Pydantic | `id`, `role`, `content: list[ChatContent]`, `interrupted`, `metrics`, `created_at` | LiveKit pipeline |
| `SQLiteConversationStore.Message` | dataclass | `id: int`, `conversation_id: int`, `role: str`, `content: str`, `created_at: str` | Persistence |
| `ContextManager.Message` | TypeAlias | `tuple[str, str, str]` = `(message_id, role, content)` | Context assembly |
| `Compaction Message` | Protocol | `id: int`, `role: str`, `content: str` | Compaction window selection |

### 8.2 Recommended Adapter Strategy

**Do NOT change Phase 2-4 APIs.** Use thin adapters at boundaries:

```python
# In AssistantSession:
def _lk_messages_to_context_messages(self, lk_messages: list[ChatMessage]) -> list[tuple[str, str, str]]:
    return [(msg.id, msg.role, msg.text_content or "") for msg in lk_messages if msg.text_content]

def _context_messages_to_lk_chat_context(self, messages: list[tuple[str, str, str]]) -> ChatContext:
    ctx = ChatContext.empty()

        if content.strip():
            ctx.add_message(role=role, content=[content], id=msg_id)

def _sqlite_messages_to_context_messages(self, sqlite_messages: list[Message]) -> list[tuple[str, str, str]]:
    return [(str(m.id), m.role, m.content) for m in sqlite_messages]
```

### 8.3 Conversation ID Handling

- LiveKit: `ChatMessage.id` = string UUID (`item_...`)
- SQLite: `Message.id` = integer AUTOINCREMENT
- ContextManager: `message_id` = string (accepts both)
- **Strategy:** Store both mappings. Use SQLite integer IDs for compaction (requires int). Use LiveKit string IDs for context assembly.

## SECTION 9 — TOOL CALLS

### 9.1 Current Tool Call Flow

```
LLM generates FunctionCall (ChatChunk with tool_calls)
    │
    ▼
AgentActivity._pipeline_reply_task_impl()
    │
    ├─ perform_tool_executions()
    │       ├─ tool_ctx = ToolContext(tools)
    │       ├─ function_stream = llm_gen_data.function_ch
    │       ├─ For each FunctionCall:
    │       │       ├─ _tool_execution_started_cb → speech_handle._item_added([fnc_call])
    │       │       ├─ _tool_executor.execute() → calls MCP tool via FastMCP
    │       │       ├─ _tool_execution_completed_cb → speech_handle._item_added([fnc_call_out])
    │       │       └─ FunctionCallOutput inserted into chat_ctx
    │       └─ Returns tool_output
    │
    ▼
Assistant message with tool calls + results → added to chat_ctx
```

### 9.2 MCP Tool Integration

- `agent_friday.py` registers `mcp_servers=[mcp.MCPServerHTTP(url="http://127.0.0.1:8000/sse")]`
- LiveKit's `MCPServerHTTP` discovers tools via SSE
- Tools become `llm.Tool` objects in `agent.tools`
- Tool execution happens in `AgentActivity._tool_executor` → calls MCP server

### 9.3 Preserving MCP Behavior with Custom Context

**The custom context does NOT affect tool calling.** Tools are passed separately to `llm.chat(chat_ctx, tools=tools)`. The LLM sees:
1. Our assembled context (messages)
2. Tool definitions (from `agent.tools` + MCP servers)

**No changes needed to tool flow.** Just ensure:
- `agent.tools` includes MCP tools (already done in `agent_friday.py`)
- Custom `ChatContext` doesn't strip `FunctionCall`/`FunctionCallOutput` items from previous turns (our `snapshot_to_chat_context` should preserve them if present in recent messages)

### 9.4 Tool Call Representation in ContextSnapshot

```python
# In snapshot_to_chat_context, preserve tool calls from recent_messages:
for msg_id, role, content in snapshot.recent_messages:
    # If content looks like tool call/result, preserve as-is
    # But ContextManager.Message doesn't distinguish — it's just (id, role, content)
    # LiveKit ChatContext handles this via ChatItem discriminator
    
# Better: include tool calls from turn_ctx in recent_messages
recent_lk_messages = turn_ctx.messages()[-20:]  # Includes FunctionCall/FunctionCallOutput items
# But ContextManager only accepts (id, role, content) tuples...
# Solution: Convert FunctionCall to developer message, FunctionCallOutput to tool message
```

**Refined approach:** Let LiveKit manage tool calls in its native format. Our `ContextSnapshot` only assembles the *semantic context* (system, user, recent conversation, memories, project). Tool calls stay in LiveKit's `ChatContext` because they're added by the tool executor *during* the LLM turn, not before.

```python
# In on_user_turn_completed:
# 1. Get recent messages FROM turn_ctx (includes prior tool calls/results)
# 2. Assemble ContextSnapshot (budgeted, with memories/project)
# 3. Build custom ChatContext from snapshot
# 4. MERGE: custom_ctx + turn_ctx's tool calls (FunctionCall/FunctionCallOutput items)
# 5. update_chat_ctx(merged_ctx)
```

## SECTION 10 — FAILURE ISOLATION

### 10.1 Failure Boundaries

```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                        FAILURE ISOLATION ARCHITECTURE                               │
└─────────────────────────────────────────────────────────────────────────────────────┘

Voice Turn
    │
    ├─► Memory Extraction FAILS
    │       │
    │       └─► Log warning, continue turn. Memory not updated this turn.
    │
    ├─► Context Assembly FAILS (memory retrieval, project context, shrinker)
    │       │
    │       └─► ContextManager already degrades gracefully (try/except, returns partial)
    │           → LLM gets reduced context but turn continues
    │
    ├─► Project Context FAILS
    │       │
    │       └─► ContextManager catches exception, omits project context
    │
    ├─► Compaction FAILS
    │       │
    │       └─► Fire-and-forget task; raw conversation intact. Log, retry next turn.
    │
    ├─► Promotion FAILS
    │       │
    │       └─► Ledger stays PENDING. Memory write may have succeeded (idempotent retry).
    │           Conversation continues.
    │
    ├─► LLM FAILS
    │       │
    │       └─► LiveKit's error handling: retry (conn_options), then session error → shutdown
    │
    └─► Tool FAILS
            │
            └─► MCP returns error envelope → LiveKit inserts FunctionCallOutput(is_error=True)
                → LLM sees error → responds appropriately
```

### 10.2 Where Boundaries Live

| Failure | Boundary Location |
|---------|-------------------|
| Memory extraction | `AssistantSession._run_memory_extraction()` — try/except, log, return |
| Context assembly | `ContextManager.assemble()` — already has try/except per subsystem |
| Project context | `ContextManager._project_context()` — try/except, returns None |
| Compaction | `CompactionService.maybe_compact()` — fire-and-forget task, try/except |
| Promotion | `PromotionCoordinator.promote_compaction()` — try/except, ledger tracks state |
| LLM | LiveKit `AgentActivity` — built-in retry, then session error |
| Tool | MCP server → LiveKit tool executor → FunctionCallOutput with error |

## SECTION 11 — ASYNC / LATENCY

### 11.1 Operations That MUST Complete Before LLM Request (SYNCHRONOUS)

| Operation | Latency Target | Reason |
|-----------|----------------|--------|
| Recent conversation retrieval | <10ms | SQLite read |
| Durable memory retrieval | <50ms | SQLite query + ranking |
| Project context retrieval | <50ms | File reads (markdown) |
| Context assembly (budgeting, rendering) | <20ms | Pure Python |
| **Total** | **<150ms** | Must not add perceptible latency |

### 11.2 Operations That MUST NOT Block Voice Response (ASYNCHRONOUS, FIRE-AND-FORGET)

| Operation | Latency | Execution Model |
|-----------|---------|-----------------|
| Memory extraction (LLM call) | 1-3s | `asyncio.create_task()` after turn |
| Compaction (LLM call) | 2-5s | `asyncio.create_task()` after turn |
| Promotion (DB writes) | 50-200ms | `asyncio.create_task()` after compaction |
| Conversation persistence | <10ms | Already sync in event handler (fast) |

### 11.3 Recommended Execution Model

```python
class AssistantSession:
    async def process_user_message(self, user_text: str) -> str:
        # 1. SYNC: Assemble context (must complete before LLM)
        snapshot = self.context_manager.assemble(...)
        custom_ctx = self._snapshot_to_chat_context(snapshot)
        await self.agent.update_chat_ctx(custom_ctx)
        
        # 2. SYNC: Generate reply (LiveKit handles streaming, tools, TTS)
        handle = self.session.generate_reply(user_input=user_text)
        assistant_text = await handle.get_text()  # Wait for full response
        
        # 3. ASYNC: Background work (fire-and-forget)
        asyncio.create_task(self._post_turn_work(
            user_text=user_text,
            assistant_text=assistant_text,
            conversation_id=self.conversation_id
        ))
        
        return assistant_text
    
    async def _post_turn_work(self, user_text, assistant_text, conversation_id):
        try:
            # Persist assistant message (already done by LiveKit event handler)
            
            # Memory extraction (every N turns)
            if self._should_extract():
                await self._run_memory_extraction(conversation_id)
            
            # Compaction check
            result = await self.compaction_service.maybe_compact(
                conversation_id, 
                self._get_all_messages(conversation_id)
            )
            if result and result.compacted:
                # Promotion is explicit — could auto-promote facts/decisions here
                await self.promotion_coordinator.promote_compaction(result.compaction, self.active_project_id)
        except Exception as e:
            logger.warning("Post-turn work failed: %s", e)
```

# friday/core/session.py

class AssistantSession:
    """Owns all stores, managers, and the LiveKit AgentSession."""
    
    def __init__(
        self,
        *,
        livekit_session: AgentSession,
        agent: FridayAgent,
        conversation_store: ConversationStore,
        memory_store: MemoryStorage,
        compaction_store: CompactionStorage,
        promotion_store: PromotionLedgerStore,
        project_service: ProjectService,
        llm_backend: LLMBackend,  # For extractor/shrinker
        config: Config,
    ):
        self._session = livekit_session
        self._agent = agent
        self._conversation_store = conversation_store
        self._memory_manager = DurableMemoryManager(memory_store)
        self._memory_extractor = MemoryExtractor(llm_backend, window_size=config.EXTRACTION_WINDOW_MESSAGES)
        self._memory_resolver = MemoryResolver()
        self._context_manager = ContextManager(
            memory_manager=self._memory_manager,
            project_context_provider=ProjectContextAdapter(project_service),
            shrinker=ContextShrinker(llm_backend),
            budget=ContextBudget(...),
        )
        self._compactor = ConversationCompactor(
            store=SQLiteCompactionStore(conversation_store.db_path),
            extractor=ConversationCompactionExtractor(llm_backend),
        )
        self._promoter = ConversationMemoryPromoter(
            promotion_store=SQLitePromotionStore(conversation_store.db_path),
            memory_manager=self._memory_manager,
            resolver=self._memory_resolver,
        )
        self._project_service = project_service
        self._conversation_id = None
        self._turn_count = 0
    
    async def start(self):
        self._conversation = self._conversation_store.create_conversation()
        self._conversation_id = self._conversation.id
        # Store in LiveKit session userdata for event handler
        self._session.userdata = {
            "assistant_session": self,
            "conversation_id": self._conversation_id,
        }
    
    async def process_user_message(self, user_text: str) -> str:
        # 1. Get recent messages from LiveKit's turn_ctx (via agent)
        recent_lk = self._agent.chat_ctx.messages()[-20:]
        recent = self._lk_messages_to_context_messages(recent_lk)
        
        # 2. Assemble context
        snapshot = self._context_manager.assemble(
            system_instructions=load_system_prompt(),
            current_user_message=user_text,
            recent_messages=recent,
            conversation_id=self._conversation_id,
            active_project_id=self._get_active_project_id(),
        )
        
        # 3. Build replacement ChatContext
        custom_ctx = self._snapshot_to_chat_context(snapshot)
        await self._agent.update_chat_ctx(custom_ctx)
        
        # 4. Generate reply via LiveKit
        handle = self._session.generate_reply(user_input=user_text)
        assistant_text = await handle.get_text()
        
        # 5. Fire-and-forget background work
        self._turn_count += 1
        asyncio.create_task(self._post_turn_background_work(user_text, assistant_text))
        
        return assistant_text
    
    async def _post_turn_background_work(self, user_text: str, assistant_text: str):
        try:
            # Memory extraction
            if self._turn_count % config.EXTRACTION_CADENCE_TURNS == 0:
                await self._run_memory_extraction()
            
            # Compaction
            all_messages = self._conversation_store.get_all_messages(self._conversation_id)
            result = self._compactor.compact(all_messages, conversation_id=self._conversation_id, force=False)
            if result.compacted:
                # Auto-promote eligible items (facts, decisions)
                self._promoter.promote(result.compaction, project_id=self._get_active_project_id())
        except Exception as e:
            logger.warning("Background work failed: %s", e)
    
    async def stop(self):
        self._conversation_store.close()
        # memory_store, etc. closed via conversation_store (same DB) or separately
```

## SECTION 15 — FINAL DECISION

```
M7.1 RECOMMENDATION
--------------------
Integration strategy:
Use LiveKit's designed extension point: override `Agent.on_user_turn_completed()` to
assemble FRIDAY's ContextSnapshot, build a replacement ChatContext, and call
`agent.update_chat_ctx()`. This preserves 100% of LiveKit's voice pipeline (STT,
TTS, VAD, streaming, interruptions, MCP tools) while injecting FRIDAY's budgeted,
memory-aware context immediately before the LLM call.

Why:
- LiveKit explicitly documents on_user_turn_completed as "good opportunity to update
  the chat context or edit the new message before it is sent to the LLM"
- generate_reply(chat_ctx=...) and agent.update_chat_ctx() are public APIs
- Zero risk to tool calling, streaming, interruption handling
- Minimal code change (~200 lines in new AssistantSession + Agent override)
- Testable with fake LLMBackend and fake stores

LIVEKIT SHOULD:
1. Continue owning STT, VAD, TTS, audio I/O, turn detection, interruption handling
2. Continue managing AgentSession lifecycle, chat context persistence, tool execution
3. Continue providing MCP server integration for tools
4. Call Agent.on_user_turn_completed before each LLM turn (already does)

LIVEKIT SHOULD NOT:
1. Be replaced for LLM inference (keep Agent.llm_node → llm.chat())
2. Be replaced for tool execution (keep MCP server + AgentActivity._tool_executor)
3. Have its chat context management bypassed (use update_chat_ctx, not direct manipulation)

ASSISTANT CORE:
- responsibility: Own conversation turn orchestration, context assembly, store lifecycles
- boundary: Single class (AssistantSession) that wraps LiveKit AgentSession
- lifecycle owner: All SQLite stores, MemoryManager, ContextManager, Compactor, Promoter, ProjectService

CONTEXT FLOW:
User speech → STT → LiveKit turn_ctx
    ↓
Agent.on_user_turn_completed(turn_ctx, new_message)
    ↓
AssistantSession.assemble_context_for_turn()
    ├─ recent_messages = turn_ctx.messages()[-N:]
    ├─ conversation_id = session.userdata
    ├─ active_project_id = ProjectService.active_project()
    ├─ ContextManager.assemble(...) → ContextSnapshot
    ├─ snapshot_to_chat_context(snapshot) → custom ChatContext
    └─ await agent.update_chat_ctx(custom_ctx)
    ↓
LiveKit _pipeline_reply_task → llm.chat(custom_ctx, tools)
    ↓
Streaming response → TTS → User

TOOL FLOW:
Unchanged. Tools registered on FridayAgent → discovered via MCP → executed by
AgentActivity._tool_executor → FunctionCall/FunctionCallOutput inserted into
LiveKit chat context during turn. Custom context only affects PRE-LLM context.

BACKGROUND WORK:
Fire-and-forget asyncio tasks after assistant response completes:
- Memory extraction (every N turns, calls MemoryExtractor → Resolver → DurableMemoryManager)
- Compaction check (ConversationCompactor.compact, advances boundary if threshold met)
- Promotion (explicit, ConversationMemoryPromoter.promote after compaction)
All wrapped in try/except; failures logged, never block voice turn.

NEXT IMPLEMENTATION:
M7.1 — AssistantSession + FridayAgent.on_user_turn_completed override
  Files: friday/core/session.py, friday/core/protocols.py, agent_friday.py (minimal)

BLOCKERS:
- None. All Phase 2-4 libraries exist with stable protocols.
- LiveKit APIs used are stable public interfaces.

RISKS:
1. LiveKit ChatContext item ordering — must preserve FunctionCall/FunctionCallOutput
   from previous turns. Solution: merge custom context with turn_ctx's tool items.
2. SQLite connection lifetime — AssistantSession must outlive LiveKit callbacks.
   Solution: AssistantSession owns stores; shutdown_callback closes stores AFTER session.
3. Context budget too aggressive → LLM loses needed history. Solution: tune config
   CONTEXT_MAX_INPUT_UNITS; monitor estimated_units in tests.

FILES LIKELY TO CHANGE:
- agent_friday.py                    (minimal: pass AssistantSession to FridayAgent)
- friday/core/session.py             (NEW: AssistantSession implementation)
- friday/core/protocols.py           (NEW: AssistantSession protocol)
- friday/core/adapters.py            (NEW: ProjectContextAdapter, message converters)
- friday/context/manager.py          (MINOR: ensure ProjectContextProvider protocol public)

NO IMPLEMENTATION WAS PERFORMED.

# ADR-026 — Master Agent Orchestration and Local Machine Control

## **Status**

Accepted

## **Date**

2026-08-19

---

### Context

FRIDAY is currently a voice assistant with independent, hardened subsystems
(memory, context, filesystem, projects, conversation compaction) and an MCP
tool layer. ADR-001 established MCP as the tool execution layer and ADR-002
established "AI is a capability, not the foundation." Existing guidance
(FRIDAY_BUILD_LOG §35) is "capabilities before orchestration."

Future direction is now recorded: FRIDAY is intended to become a **master
agent orchestrator** that delegates bounded tasks to specialized worker
agents and independently verifies their results, and to gain **controlled
local-machine interaction** through explicit, permissioned tools.

This ADR records the direction, the locked principles, and the deliberately
open implementation details. It does NOT describe a currently implemented
system. Nothing here is implemented in the current phase.

---

### Decision

FRIDAY is the decision-maker and orchestrator. Worker agents execute bounded
tasks. Verifier agents independently evaluate results. Local-machine tools
are explicitly permissioned. Memory/context/compaction/task state remain
conceptually separate storage concepts.

#### 1. Local machine control

FRIDAY will eventually be capable of controlled local-machine interaction:

- opening applications
- opening URLs
- opening files/folders
- inspecting running processes
- executing approved local commands

Architectural boundary:

> FRIDAY must NOT initially receive unrestricted arbitrary shell access.

Local-machine capabilities are exposed as explicit, permissioned
tools/capabilities. Example future tools (not a locked final API):

```
open_application
close_application
open_url
open_file
open_folder
launch_command
get_running_processes
```

The future local-system tool layer must support permission boundaries and
must distinguish safe application/file operations from potentially dangerous
arbitrary command execution. The tools are NOT implemented now.

#### 2. FRIDAY as master orchestrator

FRIDAY will become more than a voice assistant:

``` text
User
  ↓
FRIDAY
  ↓
Task understanding / planning
  ↓
Agent selection
  ↓
Worker agent
  ↓
Independent verifier
  ↓
FRIDAY
  ↓
accept / retry / escalate
```

FRIDAY determines when a task is better delegated to an external/specialized
agent rather than attempting the entire task itself.

#### 3. Agent registry

Individual agent implementations are NOT hard-coded into FRIDAY's core
reasoning layer. A future **Agent Registry** describes what an agent can do:

``` text
agents/
├── opencode/
│   ├── manifest
│   └── adapter
├── hermes/
│   ├── manifest
│   └── adapter
└── verifier/
    ├── manifest
    └── adapter
```

Exact implementation is OPEN. A registry manifest describes, for example:

- capabilities
- permissions
- supported task types
- input contract
- output contract
- execution mechanism

FRIDAY selects agents based on capability rather than knowing every agent's
internal implementation.

#### 4. Initial worker agents

The initial architecture should support specialized workers such as:

- **OpenCode** — primary coding/software-engineering worker: repository
  modification, implementation, debugging, testing, refactoring.
- **Hermes** — general-purpose/operator worker: terminal/filesystem work,
  web/browser tasks, broader autonomous operations, delegation where
  appropriate.

These are initial candidate workers, not permanent architectural
dependencies. The orchestration layer uses adapters/contracts so additional
agents can be added later without changing the core orchestrator.

#### 5. Independent verifier

A separate verifier/reviewer agent is a first-class architectural component.
The worker that performs a task must NOT automatically be trusted to declare
its own work correct.

The verifier receives:

- original task contract
- acceptance criteria
- worker changes/results
- test results
- relevant repository state

It returns a structured result:

``` text
PASS
FAIL
NEEDS_REVIEW
```

The verifier must be independent from the worker whenever practical. A
failed verification may cause FRIDAY to:

- return the task to the worker with feedback
- select another worker
- retry
- escalate to the user

Exact retry limits and policies are OPEN.

#### 6. Task contract

Future orchestration introduces an explicit **Task Contract** with
conceptual fields:

- task ID
- objective
- repository/workspace
- constraints
- acceptance criteria
- expected outputs
- relevant context
- execution permissions

Example:

``` text
TASK
ID: TASK-042

Objective:
Implement X.

Repository:
~/Desktop/friday

Constraints:
- Do not modify Phase 2
- Use existing MemoryResolver
- No new dependencies

Acceptance criteria:
- tests pass
- Ruff clean
- no regressions

Expected output:
- files changed
- test results
- verification report
- architectural concerns
```

The exact schema is OPEN. The important decision is that worker agents
receive explicit, bounded task contracts rather than only free-form
natural-language requests.

#### 7. Orchestration loop

Future orchestration follows this conceptual lifecycle:

``` text
FRIDAY
  ↓
create Task Contract
  ↓
select worker
  ↓
execute worker
  ↓
collect result
  ↓
independent verifier
  ↓
PASS ───────────────→ accept
  │
  FAIL ──────────────→ retry/reassign
  │
  NEEDS_REVIEW ──────→ human escalation
```

The orchestration system should maintain execution state and results. No
Session model is invented merely to represent this now. Task/execution
state will be designed during the future orchestration phase.

#### 8. Security / permission boundary

FRIDAY should NOT initially have unrestricted authority over:

- arbitrary shell commands
- filesystem deletion
- credentials
- system configuration
- network access
- privileged operations

Agent capabilities are permissioned. Workers receive only the permissions
required by their task. The verifier has enough access to inspect and test
work but does not automatically inherit unrestricted worker privileges.
Exact sandboxing and permission mechanisms are OPEN.

#### 9. Relation to memory / context

The existing memory/context architecture remains authoritative. The future
orchestration layer should eventually use:

``` text
Memory      → persistent user/project knowledge
Context     → per-invocation working context
Compaction  → persistent conversation knowledge/context
Task state  → future execution state
```

These concepts are NOT collapsed into one storage mechanism. Worker results
and important task outcomes may eventually become inputs to FRIDAY's
memory/compaction systems through explicit pipelines. That integration is
NOT implemented now.

#### 10. Architectural target

``` text
User
  ↓
FRIDAY
  ├── Memory / Context
  ├── Task understanding
  ├── Planner / Orchestrator
  │      ├── Agent Registry
  │      ├── OpenCode
  │      ├── Hermes
  │      └── future workers
  │
  ├── Verifier
  │
  └── Local System Tools
         ├── application control
         ├── file/folder operations
         ├── URL opening
         └── controlled command execution
```

Key architectural principle:

> FRIDAY is the decision-maker/orchestrator. Worker agents execute bounded
> tasks. Verifier agents independently evaluate results. Local-machine tools
> are explicitly permissioned. Memory/context remain separate from
> task/execution state.

#### 11. Locked vs open

**LOCKED:**

1. FRIDAY is intended to become a master agent orchestrator.
2. Worker agents are delegated bounded tasks rather than given unrestricted
   autonomy.
3. OpenCode is an initial coding-worker target.
4. Hermes is an initial general/operator-worker target.
5. An independent verifier is part of the architecture.
6. Workers receive explicit task contracts.
7. Verification occurs against acceptance criteria, not merely worker
   self-report.
8. FRIDAY may retry, reassign, or escalate based on verification.
9. Local-machine control will be exposed through explicit tools.
10. Arbitrary unrestricted local command execution is NOT the initial
    security model.
11. Agent implementations are accessed through adapters/registry rather than
    hard-coded into FRIDAY's core.
12. Memory/context/compaction/task state remain conceptually separate.

**OPEN:**

- exact Agent Registry schema
- exact Task Contract schema
- exact execution protocol
- OpenCode adapter implementation
- Hermes adapter implementation
- verifier implementation
- verifier model/agent choice
- retry limits
- task scheduling
- concurrency
- agent lifecycle
- sandboxing implementation
- permission model details
- local command allowlist
- human approval boundaries
- task-state persistence
- worker result persistence
- how task outcomes feed memory
- how agents are discovered/installed
- whether agents can delegate to other agents

---

### Alternatives Considered

- Hard-code agent implementations into FRIDAY's core reasoning layer:
  rejected — couples the orchestrator to each worker and blocks adding
  agents later.
- Give FRIDAY unrestricted local shell access: rejected — the initial
  security model is explicit, permissioned tools, not arbitrary command
  execution.
- Trust the worker's self-report without verification: rejected — the
  verifier is a first-class architectural component; verification occurs
  against acceptance criteria.
- Free-form natural-language task delegation without task contracts:
  rejected — workers receive explicit, bounded task contracts.
- Collapse memory/context/compaction/task state into one storage mechanism:
  rejected — these remain conceptually separate (see ADR-004, ADR-024,
  ADR-025).

---

### Consequences

Benefits:

- Clear architectural target for the future orchestration phase.
- Explicit security boundary for local-machine interaction from the start.
- Decoupled orchestrator/worker/verifier roles; extensible agent model.
- Task state and execution state deferred to their own design phase instead
  of a premature Session model.

Drawbacks:

- Substantial future engineering work remains OPEN (registry, contracts,
  adapters, verifier, permissions).
- Local-machine and agent orchestration must not be conflated with the
  currently implemented memory/context/compaction subsystems.

Deferred (OPEN):

- everything listed under the OPEN section above; nothing is implemented in
  the current phase.

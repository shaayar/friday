# ADR-025 — Compaction Memory Promotion

## **Status**

Accepted

## **Date**

2026-08-18

---

### Context

Phase 4 (M1–M5) implemented persistent conversation compaction
(`friday/compaction/`): bounded windows of raw conversation are distilled
into validated `ConversationCompaction` records persisted in
conversations.db. ADR-024 defined compaction output as feeding Knowledge
Retrieval / ContextManager for runtime context.

A separate Phase 3 subsystem distills durable knowledge from raw
transcripts into memory.db via `MemoryCandidate` → `MemoryResolver` →
`DurableMemoryManager`.

The M6 readiness review surfaced a destination question: may compaction
also feed the durable-memory pipeline? ADR-024 was silent on this, and two
readings (knowledge retrieval only vs. also durable memory) were both
plausible. This ADR locks the resolution before implementation.

---

### Decision

Conversation compaction is persistent conversation history/context. It is
NOT itself durable memory. It MAY optionally feed durable-memory
promotion.

``` text
Conversation
    ↓
Compaction
    ├──→ Knowledge Retrieval → ContextManager   (primary, per ADR-024)
    │
    └──→ optional memory promotion
            ↓
        MemoryCandidate
            ↓
        MemoryResolver
            ↓
          memory.db
```

Explicit principle:

> Conversation knowledge and durable memory remain distinct concepts.

Promotion is an optional projection from compaction into durable memory,
not a conversion of the compaction record itself into memory.

#### Category promotion policy

- `summary` — NEVER promoted.
- `facts` — eligible for promotion.
- `decisions` — eligible only when they represent a durable project
  decision.
- `changes` — NOT automatically promoted. May be deterministically
  reclassified as a durable fact/decision in future work.
- `open_questions` — NEVER promoted.

No new `MemoryType` values are introduced.

#### Fact scope

Fact scope is determined by the subject of the fact, not merely by the
presence of an active project.

- "I use Ubuntu." → `USER_FACT`, `project_id=None`
- "FRIDAY uses Python." → `PROJECT_FACT`, `project_id=<deterministic>`

An active project does not coerce unrelated user facts into PROJECT scope.

#### Decision scope

There is currently no `USER_DECISION` MemoryType. Durable decision
promotion therefore requires a `project_id`. If no deterministic
`project_id` is available, project decision promotion is skipped.
`project_id` is never invented from LLM output.

#### Confidence

The compaction LLM does not assign durable-memory confidence. Promotion
assigns `MemoryConfidence.EXPLICIT`. The existing `MemoryResolver` may
deterministically demote it to `TENTATIVE` where its hedged-language rules
require that. Promotion NEVER assigns `INFERRED`. The resolver remains
responsible for all final confidence constraints.

#### Project identity

`project_id` is supplied only by the deterministic caller/orchestrator.
The LLM cannot create, infer, or override `project_id`.

If `project_id` is unavailable:

- `USER_FACT` promotion may proceed.
- `PROJECT_FACT` promotion is skipped.
- `PROJECT_DECISION` promotion is skipped.

#### Promotion timing

Promotion is strictly downstream of successful compaction persistence.
Compaction save advances the compaction boundary. Promotion failure never
rolls back successful compaction.

For the current implementation phase, promotion is explicitly invocable.
Background/automatic promotion is deferred until a runtime/orchestration
seam exists. No background infrastructure is part of M6.

#### Idempotency (promotion ledger)

No `promoted` boolean is added to `CompactionItem` (per Phase 4 M1).
Promotion tracking uses a ledger keyed by the deterministic
`CompactionItem.item_id`. The ledger lives in conversations.db.

Minimum lifecycle:

``` text
PENDING
PROMOTED
REJECTED
```

- Transient failures leave the item PENDING.
- PROMOTED: subsequent normal promotion is a no-op.
- REJECTED: subsequent normal promotion is a no-op.
- Explicit reconsideration may move REJECTED → PENDING → PROMOTED, or
  REJECTED → PENDING → REJECTED. Reconsideration must be explicitly
  requested.

#### Ledger purpose

The ledger exists to answer:

- Was this compaction item considered?
- Was it promoted?
- Was it rejected? Why?
- Which memory ID(s) resulted?
- Has it been retried?
- What happened during the last attempt?

The ledger is promotion bookkeeping and audit state. It is NOT a
replacement for memory.db. Exact physical columns remain an implementation
detail provided these guarantees are preserved.

#### Atomicity and consistency

All durable-memory writes go through `DurableMemoryManager.apply_batch()`.
Memory writes are atomic within memory.db. The ledger is stored in
conversations.db. No cross-database transactions are invented.

Consistency model:

1. Build candidates/resolutions.
2. Apply the memory batch atomically (memory.db).
3. Update the promotion ledger atomically (conversations.db).

If memory succeeds but the ledger update fails:

- the memory remains;
- the ledger remains PENDING;
- retry reconciles using deterministic item provenance before attempting
  another promotion.

Exactly-once across the two databases is NOT promised. The system instead
guarantees idempotent, eventually reconciled promotion.

#### Failure isolation

- memory.db unavailable → promotion fails safely; compaction remains
  intact; ledger remains PENDING; retry is possible.
- Resolver REJECT → no memory is created; compaction remains unchanged;
  ledger becomes REJECTED with reason.
- Transient batch failure → memory batch rolls back; ledger items remain
  PENDING.
- Malformed compaction item → defensive rejection; never write invalid
  memory.
- Missing project context → skip project-scoped promotion; user-scoped
  promotion may continue.

No automatic retry loops.

#### Existing memory pipeline

Promotion must use the existing pipeline:

``` text
CompactionItem
    ↓
MemoryCandidate
    ↓
MemoryResolver
    ↓
DurableMemoryManager.apply_batch()
    ↓
memory.db
```

The compaction subsystem must NOT directly write memory.db. The
`MemoryResolver` remains the authority for:

- duplicate detection
- contradiction handling
- confidence constraints
- CREATE/SUPERSEDE/REJECT decisions

#### CONVERSATION_SUMMARY

`Compaction.summary` is NOT automatically converted into
`MemoryType.CONVERSATION_SUMMARY`. Conversation summaries remain part of
the compaction/context system. The existing `CONVERSATION_SUMMARY`
MemoryType remains available for the raw conversation memory pipeline.

---

### Alternatives Considered

- Knowledge-retrieval-only (no durable-memory promotion): matches the
  letter of ADR-024 but leaves compaction-derived facts/decisions
  permanently outside durable memory.
- Unrestricted promotion (every category, LLM-assigned confidence):
  rejected — blurs the conversation-knowledge / durable-memory boundary
  and leaks LLM-controlled confidence into memory.
- `promoted` boolean on `CompactionItem`: rejected (Phase 4 M1) — mutates
  an immutable record and cannot record REJECT reasons, retries, or memory
  IDs.
- Cross-database transaction spanning conversations.db + memory.db:
  rejected — two separate SQLite databases; no cross-DB transactions are
  invented.

---

### Consequences

Benefits:

- Unambiguous architecture: compaction is context; promotion is an
  optional projection into durable memory.
- Deterministic confidence and project identity; the resolver remains the
  memory authority.
- Idempotent, auditable, retryable promotion without a `promoted` boolean.

Drawbacks:

- Promotion spans two databases (conversations.db ledger + memory.db);
  exactly-once is not promised, only idempotent eventual reconciliation.
- Two independent proposers (Phase 3 raw-transcript extraction and M6
  compaction promotion) may converge on the same fact; the resolver's
  content deduplication is the convergence point.

Deferred (OPEN):

- automatic promotion trigger
- background promotion runtime seam
- exact ledger physical schema
- retry count/backoff limits
- future deterministic reclassification of `changes`
- future promotion of additional memory categories
